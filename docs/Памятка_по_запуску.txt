Памятка 1. Запуск проекта STDO / ДокПоток IRIS на Windows
1. Подготовка (делается один раз)
Установить PostgreSQL:

скачать установщик с официального сайта;

порт оставить 5432;

пользователь: postgres;

пароль: Qwerty852 (или свой, но тогда не забыть поменять в DSN);

через pgAdmin создать базу:

sql
CREATE DATABASE iris;
Настроить DSN в config.py (под твой пароль и базу iris):

python
db_dsn: str = field(default_factory=lambda: _env_or_default(
    "IRIS_DB_DSN",
    "postgresql://postgres:ТВОЙ_ПАРОЛЬ@localhost:5432/iris",
))

def load_config() -> Config:
    return Config(
        db_dsn=os.getenv(
            "DB_DSN", "postgresql://postgres:ТВОЙ_ПАРОЛЬ@localhost:5432/iris"
        ),
        storage_root=os.getenv("STORAGE_ROOT", "./data/docs"),
        log_level=os.getenv("LOG_LEVEL", "INFO"),
    )
Создать .env в корне C:\Users\Novikova\Desktop\STDO\STDO:

text
DB_DSN=postgresql://postgres:ТВОЙ_ПАРОЛЬ@localhost:5432/iris
STORAGE_ROOT=storage
LOG_LEVEL=INFO
IRIS_DB_DSN=postgresql://postgres:ТВОЙ_ПАРОЛЬ@localhost:5432/iris
IRIS_STORAGE_ROOT=storage
IRIS_SECRET_KEY=iris-secret-key-change-in-production
IRIS_LOG_LEVEL=INFO
Установить Python‑зависимости (из корня проекта STDO):

bash
cd C:\Users\Novikova\Desktop\STDO\STDO
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Установить фронтовые зависимости (один раз):

bash
cd C:\Users\Novikova\Desktop\STDO\STDO\frontend
npm install
2. Сборка фронтенда (при изменениях UI)
Каждый раз, когда меняешь фронтенд и хочешь обновить прод‑бандл:

bash
cd C:\Users\Novikova\Desktop\STDO\STDO\frontend
npm run build
После этого в frontend/dist лежит актуальный React‑бандл, который раздаёт backend.

3. Запуск всего приложения (бэкенд + собранный фронт)
Каждый обычный запуск:

Убедиться, что служба PostgreSQL запущена:

Win+R → services.msc → служба postgresql-… в статусе «Запущена».

В консоли:

bash

(Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned) ; (& .\.venv\Scripts\Activate.ps1)

python -m uvicorn main:app --host 0.0.0.0 --port 8000
Открыть в браузере:

UI: http://127.0.0.1:8000

API docs: http://127.0.0.1:8000/docs

Health: http://127.0.0.1:8000/health

4. Режим разработки
Если нужно быстро править фронт с hot‑reload:

Запустить бэкенд с авто‑перезапуском:

bash
cd C:\Users\Novikova\Desktop\STDO\STDO
(Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned) ; (& .\.venv\Scripts\Activate.ps1)

Во втором терминале — фронт:

bash

Работать с UI по адресу из вывода npm run dev (обычно что‑то вроде http://localhost:5173), при этом API остаётся на http://127.0.0.1:8000.

5. Мини‑чеклист, если «не работает»
Uvicorn не стартует → смотреть traceback в консоли:

часто: нет подключения к БД (Postgres не запущен или DSN неправильный).

Сообщение connection refused к Postgres:

служба PostgreSQL не запущена;

порт не 5432 или база/логин/пароль не совпадают.

404 на UI по :8000:

не собран фронт (npm run build);

или логика отдачи frontend/dist в main.py выключена/изменена.

Памятка 2. Конфиги STDO / ДокПоток IRIS
1. Ключевые файлы конфигурации
config.py (корень проекта):

класс Config — базовые настройки:

db_dsn — строка подключения к PostgreSQL;

storage_root — корень файлового хранилища;

secret_key — секрет для токенов/сессий;

log_level — уровень логирования.

функция load_config() — точка входа для приложения:

подхватывает DB_DSN, STORAGE_ROOT, LOG_LEVEL из окружения;

создаёт объект Config.

.env (корень проекта):

хранит реальные параметры для конкретной машины:

DB_DSN — основной DSN для приложения;

IRIS_DB_DSN — DSN для Alembic/совместимости, тот же, что и DB_DSN;

STORAGE_ROOT / IRIS_STORAGE_ROOT — каталог данных;

IRIS_SECRET_KEY, LOG_LEVEL, IRIS_LOG_LEVEL.

alembic.ini и alembic/env.py:

alembic/env.py:

добавляет корень проекта в sys.path;

импортирует Config из config.py;

выставляет:

python
cfg = Config()
config.set_main_option("sqlalchemy.url", cfg.db_dsn)
в online‑режиме создаёт SQLAlchemy‑engine на этом URL и выполняет миграции.

2. Единый источник правды для DSN
Цель — чтобы бэкенд и Alembic всегда работали с одной и той же базой.

Минимальный набор:

text
DB_DSN=postgresql://postgres:ТВОЙ_ПАРОЛЬ@localhost:5432/iris
IRIS_DB_DSN=postgresql://postgres:ТВОЙ_ПАРОЛЬ@localhost:5432/iris
В config.py:

python
db_dsn: str = field(default_factory=lambda: _env_or_default(
    "IRIS_DB_DSN",
    "postgresql://postgres:ТВОЙ_ПАРОЛЬ@localhost:5432/iris",
))

def load_config() -> Config:
    return Config(
        db_dsn=os.getenv(
            "DB_DSN", "postgresql://postgres:ТВОЙ_ПАРОЛЬ@localhost:5432/iris"
        ),
        storage_root=os.getenv("STORAGE_ROOT", "./data/docs"),
        log_level=os.getenv("LOG_LEVEL", "INFO"),
    )
)
Принцип:

если .env есть → используются значения из него;

если .env потерялся → дефолты в config.py совпадают по смыслу и указывают на ту же базу.

3. Как не плодить противоречия
Не заводить разные DSN для одного окружения:

DB_DSN и IRIS_DB_DSN должны указывать на одну и ту же базу;

если база/порт/пароль меняются — сначала меняешь .env, затем при желании дефолты в config.py.

Не править DSN только в alembic.ini:

пусть Alembic всегда берёт URL через Config, иначе БД миграций и БД приложения могут разъехаться.

Не хранить конфиденциальные данные в коде:

в config.py можно оставить «учебный» дефолт, но для реальной работы всегда использовать .env;

реальные пароли и хосты — только в .env, который не коммитится.

Памятка 3. Git / GitHub для проекта STDO
1. Подготовка (делается один раз)
Убедиться, что Git установлен:

bash
git --version
Если Git ещё не настроен на компьютере, задать имя и почту:

bash
git config --global user.name "Irina Novikova"
git config --global user.email "ТВОЙ_EMAIL"
Убедиться, что проект уже является git‑репозиторием:

bash
cd C:\Users\Novikova\Desktop\STDO\STDO
git status
Если виден статус ветки и файлов — всё в порядке.

2. Обычное сохранение изменений в GitHub
Каждый раз, когда хочешь сохранить текущее рабочее состояние перед правками:

bash
cd C:\Users\Novikova\Desktop\STDO\STDO
git status
git add .
git commit -m "Короткое описание изменений"
git push
Примеры сообщений коммита:

fix: запуск backend и alembic

refactor: чистка конфигов

feat: добавлен tender api

snapshot: состояние перед чисткой структуры

git add + git commit создают снимок текущего состояния проекта, а git push отправляет его в GitHub.

3. Снимок перед опасной чисткой / рефакторингом
Если перед удалением файлов, массовой чисткой или экспериментами нужно сделать точку возврата:

Зафиксировать изменения:

bash
cd C:\Users\Novikova\Desktop\STDO\STDO
git add .
git commit -m "Снимок состояния перед чисткой"
git push
Дополнительно создать тег:

bash
git tag -a before-cleanup -m "Состояние перед чисткой файлов и структуры"
git push origin before-cleanup
Тег — это постоянная метка на конкретном коммите, удобная как «контрольная точка». Для таких снапшотов теги подходят лучше всего.

4. Работа с ветками
Посмотреть текущую ветку:

bash
git branch
Создать новую ветку для отдельной задачи:

bash
git checkout -b cleanup/project-structure
Отправить новую ветку в GitHub:

bash
git push -u origin cleanup/project-structure
Дальше все обычные git push будут идти в неё автоматически. Пуш новой ветки через -u origin <branch> — стандартный способ привязать локальную ветку к удалённой.

5. Если изменения ещё не готовы к коммиту
Если нужно временно убрать локальные изменения и переключиться на другую задачу:

bash
git stash
Посмотреть список stash:

bash
git stash list
Вернуть последние сохранённые изменения:

bash
git stash pop
git stash подходит для временного складывания незавершённых правок, когда коммит делать рано.

6. Мини‑чеклист, если «не работает»
git commit пишет, что нечего коммитить:

значит изменения не сохранены в файлах или уже закоммичены;

проверить git status.

git push не проходит:

проверить, в какой ветке находишься: git branch;

проверить удалённый репозиторий: git remote -v;

если ветка новая, использовать:

bash
git push -u origin ИМЯ_ВЕТКИ
Нужно быстро вернуться к состоянию до чистки:

посмотреть теги:

bash
git tag
перейти на нужную точку:

bash
git checkout before-cleanup

Памятка 4. Безопасная чистка файлов и папок в Git
1. Подготовка перед чисткой
Перед удалением файлов, папок, старых конфигов и мусора всегда сначала сделать снимок состояния:

bash
cd C:\Users\Novikova\Desktop\STDO\STDO
git status
git add .
git commit -m "Снимок состояния перед чисткой"
git push
Если чистка большая — дополнительно сделать тег:

bash
git tag -a before-cleanup -m "Состояние перед чисткой файлов и структуры"
git push origin before-cleanup
Это даёт безопасную точку возврата перед рефакторингом и удалениями.

2. Как правильно удалять файлы, которые точно не нужны
Если файл или папка больше не нужны ни локально, ни в репозитории:

bash
git rm path\to\file
git rm -r path\to\folder
git commit -m "Удалены неиспользуемые файлы"
git push
git rm удаляет файл сразу и из рабочей папки, и из Git‑индекса, поэтому это самый понятный способ для осознанной чистки.

3. Если удалить нужно только из Git, но оставить локально
Например, .env, локальные данные, временные файлы, кэш, артефакты сборки.

Добавить путь в .gitignore:

text
.env
.env.local
.venv/
frontend/dist/
node_modules/
Убрать файл из Git, но не с диска:

bash
git rm --cached .env
git rm -r --cached frontend/dist
git commit -m "Убраны локальные файлы из Git"
git push
git rm --cached удаляет файл только из репозитория, но оставляет его на компьютере. Это стандартный способ перестать версионировать локальные или генерируемые файлы.

4. Если удалили руками через Проводник или IDE
Если файл уже удалён вручную, Git всё равно увидит это как изменение.

Проверить:

bash
git status
Зафиксировать удаление:

bash
git add -A
git commit -m "Удалены лишние файлы"
git push
git add -A удобно использовать при массовой чистке, потому что он подхватывает новые, изменённые и удалённые файлы сразу.

5. Как посмотреть, что удалится, перед коммитом
Перед коммитом всегда проверять:

bash
git status
git diff --name-only --cached
Если сомневаешься — не коммить сразу, а сначала пересмотри список. Это особенно важно при удалении папок, чтобы случайно не снести нужные конфиги, миграции или тесты.

6. Как откатить ошибочное удаление
Если файл удалён, но ещё не закоммичен:

bash
git restore path\to\file
Если удалена целая папка:

bash
git restore .
git restore возвращает tracked‑файлы из последнего коммита, если удаление ещё не было зафиксировано.

7. Как вернуть файл после уже сделанного коммита
Если уже закоммитила удаление, можно вернуться к старой версии:

bash
git log -- path\to\file
git checkout КОММИТ_HASH -- path\to\file
Потом сохранить возврат:

bash
git add path\to\file
git commit -m "Возвращён ошибочно удалённый файл"
git push
Git позволяет восстановить удалённый файл из предыдущих коммитов, если он когда‑то уже был сохранён в истории.

8. Мини‑чеклист, если «что‑то удалилось не то»
Файл удалён, но коммита ещё не было:

git restore path\to\file

Удаление уже закоммичено:

найти нужный коммит через git log;

вернуть файл через git checkout КОММИТ -- path\to\file

Нужно убрать секреты или приватные данные из уже запушенной истории:

обычного удаления мало;

нужно переписывать историю (git filter-repo) и менять скомпрометированные секреты.
